# Standard Traceability

| Standard or source | Engineering decision |
| --- | --- |
| CloudEvents 1.0.2 | Future event envelopes preserve source and event identity for deduplication. |
| Cowlishaw decimal arithmetic 1.70 | Billable quantities are exact decimals, never binary floating-point values. |
| RFC 9110 | At-least-once delivery is made safe by idempotent ingest of the same source key and payload. The HTTP accept surface maps `accepted` and `duplicate_replay` to 200, `rejected` to 422, and unknown routes to 404. GET journal-proposal query is a safe, idempotent pull and does not mutate `proposal_status`. POST `/v1/posting-receipt-observations` is the operator trigger that pulls an AIS receipt; GET of a stored observation is a safe read and does not call AIS. POST `/v1/ais-outbox-drains` is the explicit AIS outbox drain; empty unpublished pages skip receipt GETs; publish is POST `/outbox-events/{outbox_event_id}/publish`. POST `/v1/posting-receipt-observations` stays the #16 pull; GET `/v1/posting-receipt-observations/{idempotency_key}` stays the existing item read; GET `/v1/posting-receipt-observations` lists stored observations as a commercial statement and returns 404 across tenants. POST `/v1/credit-adjustments` records a commercial credit; GET of a stored credit is a safe tenant-scoped read and does not call AIS. POST `/v1/rate-cards` publishes a catalog version; GET of a stored card is a safe tenant-scoped presentment read and does not invent a price. POST `/v1/rate-cards` publishes an append-only catalog version; GET list, card, versions, and version routes are safe tenant-scoped reads and return 404 across tenants. POST `/v1/usage-events` stays the #5 ingest; GET `/v1/usage-events/{usage_event_id}` and GET `/v1/usage-events` present stored usage as a commercial statement and return 404 across tenants. POST `/v1/rating-runs` stays the #7 rate-a-window command; GET `/v1/rating-runs/{rating_run_id}` and GET `/v1/rating-runs` present stored rating as a commercial statement and return 404 across tenants. POST `/v1/tax-rates` and POST `/v1/tax-assessments` write append-only tax facts; GET `/v1/tax-assessments/{tax_assessment_id}` stays the existing #19 item read; GET `/v1/tax-assessments` lists stored assessments as a commercial statement and returns 404 across tenants. GET list, version, and assessment routes are safe tenant-scoped reads and return 404 across tenants. GET `/v1/invoice-drafts/{invoice_draft_id}` and GET `/v1/invoice-drafts` present a stored draft as a commercial statement and return 404 across tenants. GET `/v1/collection-cases/{collection_case_id}` and GET `/v1/collection-cases` present a stored collection case as a commercial statement and return 404 across tenants. POST `/v1/payment-intents` projects a stored collection case; GET `/v1/payment-intents/{payment_intent_id}` and GET `/v1/payment-intents` present that intent as a commercial statement and return 404 across tenants. POST `/v1/payment-receipts` applies a projected intent; GET `/v1/payment-receipts/{payment_receipt_id}` and GET `/v1/payment-receipts` present that receipt as a commercial statement and return 404 across tenants. POST `/v1/tenant-api-credentials` issues a key; GET `/v1/tenant-api-credentials` is a safe metadata list and never returns the secret; POST revoke is idempotent. GET `/healthz` stays unauthenticated. POST `/v1/webhook-subscriptions` registers an https callback; GET `/v1/webhook-subscriptions` is a safe metadata list and never returns the secret; POST revoke is idempotent; POST `/v1/webhook-deliveries` is the explicit delivery run. |
| Google AIP-158 | Journal-proposal list pages use a deterministic keyset cursor (`proposed_at`, `proposal_id`) and a bounded `page_limit` instead of a mutable offset. Invoice-draft presentment list pages use (`drafted_at`, `invoice_draft_id`). Collection-case presentment list pages use (`opened_at`, `collection_case_id`). Payment-intent presentment list pages use (`projected_at`, `payment_intent_id`). Payment-receipt presentment list pages use (`received_at`, `payment_receipt_id`). Credit-adjustment presentment list pages use (`recorded_at`, `credit_adjustment_id`). Rate-card presentment list pages use (`created_at`, `rate_card_id`). Usage-event presentment list pages use (`recorded_at`, `usage_event_id`). Rating-run presentment list pages use (`recorded_at`, `rating_run_id`). Tax-assessment presentment list pages use (`assessed_at`, `tax_assessment_id`). Posting-receipt observation presentment list pages use (`observed_at`, `posting_receipt_observation_id`). |
| Helland (2012) | Replays acknowledge the stored fact; a mutated payload is a conflict, not an update. |
| IEEE 754-2019 | Decimal interchange stays in the decimal domain; binary inexact types are rejected. |
| ISO 8601-1:2019 | `occurred_at` and usage windows are timezone-aware instants; naive timestamps fail closed. |
| FOCUS 1.4 | Cost, invoice, billing-period, and commitment data are export projections, not the internal operational schema. |
| IFRS 15 | Billing and revenue recognition remain separate; an invoice-intent draft, journal proposal, collection reminder, commercial credit adjustment, invoice-draft presentment statement, and collection-case presentment statement are consideration evidence, not proof that revenue has been earned or reversed. The operator Storybook console presents those same exact-decimal amounts and the next action (collect or credit) without claiming earned revenue. A later price concession or billing correction is variable consideration. Amounts collected on behalf of a tax authority are not usage revenue; Billing credits semantic `tax_payable` on the invoice journal and debits it on a taxed credit so AIS books do not drift. Performance-obligation and principal-versus-agent judgments belong to versioned accounting policy in AIS. |
| IFRS 18 | The Accounting Information Platform owns presentation categories, required subtotals, management-defined performance measure disclosures, and the 2027 transition; Billing does not encode statement presentation when it emits a journal proposal. |
| IFRS Accounting Taxonomy 2025 | Financial-report output remains taxonomy-versioned, with the 2025 taxonomy retained for 2026 reporting. |
| IAS 7 | Bank and settlement facts are classified and presented by Accounting rather than inferred from a payment-provider status alone. Billing proposes semantic `cash_receipt` versus `accounts_receivable` roles; AIS owns the cash-flow classification. |
| IAS 21 | Transaction, functional, and presentation currencies are separate accounting concepts; Billing preserves source currency and amounts. |
| ISO 20022-1:2026 | Bank and treasury adapters use versioned financial-message mappings rather than proprietary fields in the accounting core. Payment initiation stays a provider-neutral `payment_intent` until a later adapter projects an ISO 20022 initiation message (`pain.001`). Commercial settlement is a `payment_receipt` applied against that intent; the cash journal proposal is billing evidence for AIS, not an ISO 20022 `camt` settlement or clearing message. A commercial `credit_adjustment` is billing evidence for a credit note, not a posted ISO 20022 credit-note settlement. Invoice-draft presentment is a commercial statement, not a posted ISO 20022 invoice message. AIS pulls journal evidence and later returns a posting receipt; Billing stores the receipt as an observation and does not post it. |
| PCI DSS 4.0.1 | Payment intents, payment receipts, and credit adjustments never store card PAN, CVC, or provider charge identifiers, reducing cardholder-data scope in this repository. `POST /v1/payment-intents`, `POST /v1/payment-receipts`, `POST /v1/credit-adjustments`, `POST /v1/rate-cards`, `POST /v1/usage-events`, `POST /v1/rating-runs`, `POST /v1/tax-assessments`, and `POST /v1/posting-receipt-observations` refuse those fields on the wire. |
| RFC 2104 | Webhook deliveries sign the raw JSON body with HMAC-SHA256. The header is `X-CWL-Webhook-Signature: sha256=<hex>`. |
| RFC 9421 | HTTP Message Signatures are not implemented in this slice. Receivers verify the HMAC over the raw body rather than a structured signature input. |
| NIST SP 800-63B | Tenant API credential and webhook-subscription verifiers persist a keyed HMAC, never the recoverable secret. The plaintext secret is returned once on issue or register. |
| OWASP API2:2023 | Leaked tenant API keys are revocable bearer credentials. Unknown and revoked keys fail closed as `api_credential_invalid`. |
| SOC 2 CC6 | After a tenant has one or more active keys, every `/v1` call except credential issue requires a matching active key whose tenant equals the pin. Zero active keys remain a documented bootstrap window so AIS can keep pulling with `X-CWL-Tenant-Reference`. |
| TM Forum TMF620 | A commercial rate card is a versioned, queryable price list. Publishing writes an immutable `rate_card_version`; rating resolves that persisted version and does not invent a hidden default price. |
| ISO 4217 | Tax products are half-even rounded to a closed minor-unit exponent table (`0` for JPY and KRW, `2` for listed two-decimal currencies). Unknown currency codes fail closed. |
| OECD International VAT/GST Guidelines | A published tenant tax rate is separate from later invoice calculation. This slice applies one flat persisted rate and does not implement nexus, exemptions, or an OSS engine. |
| IAS 12 | Statutory tax presentation belongs to AIS. Billing emits semantic `tax_payable` on taxed invoice journals and debits the same role on taxed credits; AIS must map that role onto its chart. |
| PostgreSQL 18 | UUIDv7 and exact numeric persistence support ordered identifiers and monetary precision. |
