# Architecture

## System context

```text
Keyverse / credential issuers
        |
        v
Identity attribution
        |
CWL usage producers ---> Usage ledger ---> Metering ---> Rating
                                             |            |
                                             v            v
                                      quotas/budgets   invoice intent
                                                          |
                                                          v
                                              provider capability router
                                              /       |       |       \
                                           MoR     processor  PG    manual
                                                          |
                                                          v
                                               settlement reconciliation
                                                          |
                                                          v
                                             journal proposal export
                                                          |
                                                          v
                                          Accounting Information Platform
```

## Bounded contexts

- `identity_attribution`: principal and credential assignment.
- `usage_ingestion`: immutable events, measurements, corrections, and deduplication.
- `meter_registry`: versions, units, dimensions, aggregation, and billability.
- `commercial_rating`: price books, contracts, tiers, and rating outcomes.
- `entitlement_control`: grants, quotas, credits, and spend authorization.
- `invoice_management`: invoice intent, explainable lines, and commercial collection cases.
- `provider_gateway`: capability discovery, mapping, commands, webhooks, and later provider projections of payment intents.
- `settlement_reconciliation`: expected versus provider versus cash evidence.
- `accounting_export`: journal proposals and posting receipts.

## Authority matrix

| Fact | Authority |
| --- | --- |
| identity authentication | Keyverse or credential issuer |
| credential-to-principal attribution | Metering Billing Platform |
| usage and rating | Metering Billing Platform |
| invoice and provider payment state | Metering Billing Platform |
| tax document | MoR, tax provider, or jurisdictional issuer |
| chart of accounts and accounting policy | Accounting Information Platform |
| posted journal and trial balance | Accounting Information Platform |
| bank transaction | bank or treasury provider; accounting projection in Accounting Information Platform |

## Usage ingestion

`metering_billing.UsageIngestionService` is the write path for canonical usage events.  It validates the published schema, verifies the source-payload hash for the declared contract version, resolves tenant-scoped attribution, stores exact decimal measurements, and returns a receipt.  It accepts either the in-memory reference ledger or `PostgresUsageLedger`; the latter writes the event, normalized measurements, and receipt in one PostgreSQL transaction and lets tenant-scoped unique constraints arbitrate concurrent retries.  Optional batch bounds and usage queries use half-open ISO 8601 windows.  `POST /v1/usage-events` stays that ingest and refuses PAN and provider secrets.  `UsageEventPresentmentService` projects a stored event as a statement.  `GET /v1/usage-events/{usage_event_id}` is HTTP 200 for the same tenant and HTTP 404 across tenants.  `GET /v1/usage-events` lists `{usage_events, next_cursor}` ordered by `recorded_at` then `usage_event_id`.  Ingestion never writes a posted journal and never calls a payment provider.  The durable PostgreSQL path continues through rate-card publish, rating, invoice drafting, issued-invoice snapshot, tenant-scoped tax-rate publish, tax assessment, atomic `invoice.issued` outbox enqueue, tenant-scoped webhook subscription metadata, delivery attempts, and delivered status; the one-time webhook secret remains process-local.  Collection, payment, provider, recovery, and telemetry controls are not implied to be durable by this slice.

## Rate-card catalog

`metering_billing.RateCardService` publishes one tenant-scoped `rate_card` and one immutable `rate_card_version` with `rate_card_line` rows.  Header identity is `(tenant_account_id, rate_card_name)`.  Version identity is `(tenant_account_id, rate_card_id, source_payload_hash, rate_card_contract_version)`.  Each line is a two-or-more-word `snake_case` `metric_code` and an exact `Decimal` `unit_amount` greater than zero in the card currency.  An identical replay returns the same `rate_card_version`.  A later distinct line set increments `version_number`.  A published version is never edited.  `POST /v1/rate-cards` publishes a version and refuses PAN and provider secrets.  `RateCardPresentmentService` projects the stored card as a statement.  `GET /v1/rate-cards/{rate_card_id}` is HTTP 200 for the same tenant and HTTP 404 across tenants.  `GET /v1/rate-cards` lists `{rate_cards, next_cursor}` ordered by `created_at` then `rate_card_id`.  Version GET routes stay the #18 catalog reads.  This path does not apply tax, discounts, or tiered prices.

## Commercial rating

`metering_billing.UsageRatingService` is the read-and-rate path for already-stored usage.  A buyer supplies a tenant, a half-open ISO 8601 window, and a persisted rate-card version.  The service resolves that same-tenant version, aggregates billable quality only, multiplies exact quantities by the stored `unit_amount` for each matching `metric_code`, and persists append-only `rating_run` and `rating_line` rows.  Identity is `(tenant_account_id, window_started_at, window_ended_at, rate_card_version_id, usage_snapshot_hash)`.  An unknown version, a cross-tenant version, or a missing metric fails closed and does not invent a price.  An identical replay returns the same `rating_run_id` and totals.  `POST /v1/rating-runs` stays that command and refuses PAN and provider secrets.  `RatingRunPresentmentService` projects a stored run as a statement.  `GET /v1/rating-runs/{rating_run_id}` is HTTP 200 for the same tenant and HTTP 404 across tenants.  `GET /v1/rating-runs` lists `{rating_runs, next_cursor}` ordered by `recorded_at` then `rating_run_id`.  Rate a window, then draft an invoice.  Rating never drafts an invoice, never calls a payment provider, and never writes a posted journal.

## Invoice draft

`metering_billing.InvoiceDraftService` copies one stored rating run into an append-only invoice-intent draft.  Identity is `(tenant_account_id, rating_run_id)` plus the rating run's usage-snapshot hash.  An identical replay returns the same `invoice_draft_id` and exact totals.  Status is `draft` only.  The draft is a commercial document, not revenue recognition and not a posted journal.

`metering_billing.InvoicePresentmentService` projects one stored draft into a tenant-scoped statement.  Tax exclusive, tax, and inclusive come from `tax_assessment` when present and otherwise zero the tax fields.  `credited_amount` is the sum of accepted credits.  `amount_due` is inclusive minus credits and never below zero.  Collection identity and outstanding appear when a case exists.  Lines map stored draft/rating quantities onto `metric_code`, `quantity`, `unit_amount`, and `line_amount`.  `GET /v1/invoice-drafts/{invoice_draft_id}` returns the statement.  `GET /v1/invoice-drafts` lists summaries with `{invoice_drafts, next_cursor}`.  The read does not write a snapshot table, post, or call AIS.  Open the draft statement, then collect or credit.

`metering_billing.IssuedInvoiceService` copies one stored invoice draft into an append-only commercial `issued_invoice`.  Identity is `(tenant_account_id, invoice_draft_id)`.  An identical replay returns the same `issued_invoice_id` and frozen totals.  `issued_invoice_id` is an opaque generated identifier, not a statutory number.  Totals come from `tax_assessment` when present and otherwise copy the drafted exclusive total with tax zero.  Optional `due_at` is stored only when the caller supplies a valid timezone-aware instant.  `POST /v1/invoice-drafts/{invoice_draft_id}/issued-invoices` is the nested issue command and refuses PAN and provider secrets.  `IssuedInvoicePresentmentService` projects the stored snapshot.  `GET /v1/issued-invoices/{issued_invoice_id}` is HTTP 200 for the same tenant and HTTP 404 across tenants.  Item GET includes optional stored `tax_assessment_id` when the draft's commercial assessment exclusive/tax/inclusive amounts still match the frozen issued totals.  `GET /v1/issued-invoices` lists `{issued_invoices, next_cursor}` ordered by `issued_at` then `issued_invoice_id`.  Draft status stays `draft`.  First successful issue enqueues one existing #24 `invoice.issued` outbox event whose `source_id` is `issued_invoice_id` and whose `data` is a thin reference plus hash, not the invoice body.  Replay does not enqueue a second row.  The path does not capture payment, call AIS, or invent legal numbering.  Issue invoice, then collect or credit.

`metering_billing.IssuedInvoiceVoidService` records one append-only commercial `issued_invoice_void` for an unused same-tenant issued invoice.  Identity is `(tenant_account_id, issued_invoice_id)`.  An identical replay returns the same `issued_invoice_void_id` and never re-closes a collection case.  `voided_amount` is the issued tax-inclusive amount.  The issued snapshot stays `issued`.  Fail closed when the related case has a payment receipt, credit-note apply, leftover apply, or write-off, remaining no longer equals the issued amount, or the case is already settled.  An unused open or dunning case closes as `voided` at exact-zero remaining.  `POST /v1/issued-invoices/{issued_invoice_id}/voids` is the nested void command and refuses PAN and provider secrets.  `IssuedInvoiceVoidPresentmentService` projects the stored void.  `GET /v1/issued-invoice-voids/{issued_invoice_void_id}` is HTTP 200 for the same tenant and HTTP 404 across tenants.  `GET /v1/issued-invoice-voids` lists `{issued_invoice_voids, next_cursor}` ordered by `voided_at` then `issued_invoice_void_id`.  First successful void enqueues one existing #24 `invoice.voided` outbox event whose `source_id` is `issued_invoice_void_id` and whose `data` is a thin reference plus hash.  Replay does not enqueue a second row.  The void command does not compose a journal.  `AccountingExportService.propose_void_journal` and `POST /v1/issued-invoice-voids/{issued_invoice_void_id}/journal-proposals` emit one validated revenue/AR reverse of the original invoice journal.  AIS pulls that proposal through existing GET journal-proposal routes.  The path does not invent a second webhook system, AIS call, or statutory numbering.  Void an unused issue, compose the journal, then let AIS pull; do not reuse `settled`.  `operator_console` Storybook presents one unused issued-invoice void with exact inclusive voided amount.

`metering_billing.IssuedCreditNoteService` copies one stored credit adjustment into an append-only commercial `issued_credit_note`.  Identity is `(tenant_account_id, credit_adjustment_id)`.  An identical replay returns the same `issued_credit_note_id` and frozen credit totals.  `issued_credit_note_id` is an opaque generated identifier, not a statutory number.  Totals copy stored `tax_exclusive_amount`, `tax_amount`, and inclusive `credit_amount`.  `issued_invoice_id` is stored only when an issued invoice already exists for the same draft.  The snapshot copies the closed `credit_reason_code` and invents no lines.  `PostgresUsageLedger` persists the issued row with tenant-scoped composite foreign keys, exact `numeric` amounts, `uuidv7()` identifiers, and `issued_credit_note_status`.  Insert and outbox enqueue share one PostgreSQL transaction.  Replay of the same tenant and credit does not insert a second row.  A crash after insert and before enqueue is healed by the next replay.  Rejected issue writes zero rows.  `MemoryUsageLedger` remains the deterministic reference adapter.  `POST /v1/credit-adjustments/{credit_adjustment_id}/issued-credit-notes` is the nested issue command and refuses PAN and provider secrets.  `IssuedCreditNotePresentmentService` projects the stored snapshot.  `GET /v1/issued-credit-notes/{issued_credit_note_id}` is HTTP 200 for the same tenant and HTTP 404 across tenants.  Those GET presentment contracts stay unchanged when the row is loaded from PostgreSQL.  Item GET includes optional stored `tax_assessment_id` when the draft's commercial assessment still reproduces the frozen credit exclusive/tax split.  `GET /v1/issued-credit-notes` lists `{issued_credit_notes, next_cursor}` ordered by `issued_at` then `issued_credit_note_id`.  Credit status stays `recorded`.  The validated journal remains available for AIS.  First successful issue enqueues one existing #24 `credit_note.issued` outbox event whose `source_id` is `issued_credit_note_id` and whose `data` is a thin reference plus hash.  Replay does not enqueue a second row.  The path does not capture payment, call AIS, or invent legal numbering.  Issue the credit note; the validated journal remains available for AIS.

`metering_billing.IssuedCreditNoteVoidService` records one append-only commercial `issued_credit_note_void` for an unused same-tenant issued credit note.  Identity is `(tenant_account_id, issued_credit_note_id)`.  An identical replay returns the same `issued_credit_note_void_id`.  `voided_amount` is the issued tax-inclusive credit.  The issued snapshot stays `issued`.  `PostgresUsageLedger` persists the unused void with tenant-scoped composite foreign keys, exact `numeric` amounts, `uuidv7()` identifiers, and `issued_credit_note_void_status`.  Insert and outbox enqueue share one PostgreSQL transaction.  Replay of the same tenant and issued credit note does not insert a second row.  A crash after insert and before enqueue is healed by the next replay.  Rejected void writes zero rows.  Fail closed when the note has already been applied, is missing or cross-tenant, or currency mismatches.  Collection remaining is unchanged because the note cannot have been applied.  After a void exists, apply fail-closes as `issued_credit_note_voided`.  `POST /v1/issued-credit-notes/{issued_credit_note_id}/voids` is the nested void command and refuses PAN and provider secrets.  `IssuedCreditNoteVoidPresentmentService` projects the stored void.  `GET /v1/issued-credit-note-voids/{issued_credit_note_void_id}` is HTTP 200 for the same tenant and HTTP 404 across tenants.  Those GET presentment contracts stay unchanged when the row is loaded from PostgreSQL.  `GET /v1/issued-credit-note-voids` lists `{issued_credit_note_voids, next_cursor}` ordered by `voided_at` then `issued_credit_note_void_id`.  First successful void enqueues one existing #24 `credit_note.voided` outbox event whose `source_id` is `issued_credit_note_void_id` and whose `data` is a thin reference plus hash.  Replay does not enqueue a second row.  The void command does not compose a journal.  `AccountingExportService.propose_credit_note_void_journal` and `POST /v1/issued-credit-note-voids/{issued_credit_note_void_id}/journal-proposals` emit one validated AR/revenue reverse of the original credit journal.  AIS pulls that proposal through existing GET journal-proposal routes.  The path does not invent a second webhook system, VAT register, NTS filing, statutory account, negative invoice, or AIS call.  Void an unused issued credit note, compose the journal, then let AIS pull.  `operator_console` Storybook presents one unused issued-credit-note void with exact voided amount.

`metering_billing.CreditNoteApplicationService` applies one stored issued credit note onto one open same-tenant collection case.  Identity is `(tenant_account_id, issued_credit_note_id)`.  An identical replay returns the same `credit_note_application_id` and does not reduce outstanding again.  Applied amount is the exact issued tax-inclusive credit.  `PostgresUsageLedger` persists the application with tenant-scoped composite foreign keys, exact `numeric` amounts, `uuidv7()` identifiers, and `credit_note_application_status`.  Replay of the same tenant and issued credit note does not insert a second row.  A crash after insert and before enqueue is healed by the next replay.  Rejected apply writes zero rows.  Currency mismatch, settled case, remaining that would go negative, invoice mismatch, and a voided unused note fail closed.  `POST /v1/collection-cases/{collection_case_id}/credit-note-applications` is the nested apply command and refuses PAN and provider secrets.  `CreditNoteApplicationPresentmentService` projects the stored application and the current remaining outstanding.  `GET /v1/credit-note-applications/{credit_note_application_id}` is HTTP 200 for the same tenant and HTTP 404 across tenants.  Those GET presentment contracts stay unchanged when the row is loaded from PostgreSQL.  `GET /v1/credit-note-applications` lists `{credit_note_applications, next_cursor}` ordered by `applied_at` then `credit_note_application_id`.  First successful apply enqueues one existing #24 `credit_note.applied` outbox event whose `source_id` is `credit_note_application_id` and whose `data` is a thin reference plus hash.  Replay does not enqueue a second row.  The path does not invent a journal, tax unwind, second webhook system, statutory numbering, write-off, settlement, or payment capture.  Apply the issued credit note, then collect the residual.

`metering_billing.CollectionCaseSettlementService` settles one same-tenant open collection case whose remaining outstanding is exact zero.  Identity is `(tenant_account_id, collection_case_id)`.  An identical replay returns the same `collection_case_settlement_id` and never double-settles.  Outstanding that is not zero, an already-settled case, a voided case, and a tenant mismatch fail closed.  Implicit #12/#17/#45 settle-when-zero on positive apply paths stays.  `POST /v1/collection-cases/{collection_case_id}/settlements` is the nested settle command and refuses PAN and provider secrets.  `CollectionCaseSettlementPresentmentService` projects the stored settlement and the current remaining outstanding.  `GET /v1/collection-case-settlements/{collection_case_settlement_id}` is HTTP 200 for the same tenant and HTTP 404 across tenants.  `GET /v1/collection-case-settlements` lists `{collection_case_settlements, next_cursor}` ordered by `settled_at` then `collection_case_settlement_id`.  First successful settle enqueues one existing #24 `collection.settled` outbox event whose `source_id` is `collection_case_settlement_id` and whose `data` is a thin reference plus hash.  Replay does not enqueue a second row.  The path does not invent a journal, tax unwind, second webhook system, statutory numbering, write-off, or payment receipt.  Settle the zero-outstanding case, then wait.  `operator_console` Storybook presents one leftover write-off settle-when-zero with exact-zero remaining.

`metering_billing.CollectionDisputeService` holds one same-tenant open or dunning collection case as a commercial dispute.  Identity is `(tenant_account_id, collection_case_id)`.  An identical replay returns the same `collection_dispute_id` and never changes remaining outstanding.  `PostgresUsageLedger` persists the collection dispute with tenant-scoped composite foreign keys, exact `numeric` amounts, `uuidv7()` identifiers, and `collection_dispute_status`.  Replay of the same tenant and collection case does not insert a second row.  A crash after insert and before the existing `dispute.held` outbox enqueue is healed by the next replay.  On hold `duplicate_replay`, a case still `open` or `dunning` flips to `disputed` once.  Rejected hold writes zero rows.  Dispute status is `held`.  Case status becomes `disputed`.  Remaining stays the current exact-decimal snapshot.  Missing case, settled case, voided case, already-disputed case without a stored row, and currency mismatch fail closed.  New dunning, payment receipt, credit apply, leftover apply, write-off, settle-when-zero, and void fail closed while held.  `POST /v1/collection-cases/{collection_case_id}/disputes` is the nested hold command and refuses PAN and provider secrets.  `CollectionDisputePresentmentService` projects the stored hold and the current remaining outstanding.  `GET /v1/collection-disputes/{collection_dispute_id}` is HTTP 200 for the same tenant and HTTP 404 across tenants.  `GET /v1/collection-disputes` lists `{collection_disputes, next_cursor}` ordered by `held_at` then `collection_dispute_id`.  First successful hold enqueues one existing #24 `dispute.held` outbox event whose `source_id` is `collection_dispute_id` and whose `data` is a thin reference plus hash, including exact remaining outstanding at hold.  Replay does not enqueue a second row.  The path does not invent a journal, second webhook system, write-off, settlement, void rewrite, statutory numbering, payment capture, or AIS call.  Hold the disputed case, then wait.  `operator_console` Storybook presents one held dispute with exact remaining.

`metering_billing.CollectionDisputeReleaseService` releases one same-tenant held `collection_dispute` in place.  Identity is `(tenant_account_id, collection_dispute_id)`.  An identical replay returns the same `collection_dispute_id` and never changes remaining outstanding.  `PostgresUsageLedger` flips the same persisted hold row to `released` and stores `released_at`.  A crash after the row flip and before restoring the case is healed by the next replay when the case is still `disputed`.  Rejected release writes zero rows.  Dispute status becomes `released`.  Case status returns to `open`, or to `dunning` when stored notices already exist.  Remaining stays the current exact-decimal snapshot.  Missing dispute, not-held dispute, missing case, settled case, voided case, and currency mismatch fail closed.  After release, dunning, payment receipt, credit apply, leftover apply, write-off, settle-when-zero, and void follow the existing open-case rules.  A later hold of the same case fail-closes as `collection_dispute_released`.  `POST /v1/collection-disputes/{collection_dispute_id}/releases` is the nested release command and refuses PAN and provider secrets.  `CollectionDisputeReleasePresentmentService` projects the stored release and the current remaining outstanding.  `GET /v1/collection-dispute-releases/{collection_dispute_id}` is HTTP 200 for the same tenant and HTTP 404 across tenants or still-held rows.  `GET /v1/collection-dispute-releases` lists `{collection_dispute_releases, next_cursor}` ordered by `released_at` then `collection_dispute_id`.  First successful release enqueues one existing #24 `dispute.released` outbox event whose `source_id` is `collection_dispute_id` and whose `data` is a thin reference plus hash, including exact remaining outstanding at release.  Replay does not enqueue a second row.  The path does not invent a journal, second webhook system, write-off, settlement, void rewrite, statutory numbering, payment capture, or AIS call.  Release the hold, then collect or dunn.  `operator_console` Storybook presents that released/fail-close remaining snapshot.

`metering_billing.CollectionWriteOffService` writes off leftover remaining on one same-tenant open collection case.  Identity is `(tenant_account_id, collection_case_id)`.  An identical replay returns the same `collection_write_off_id` and never re-zeros outstanding.  The write-off amount is the current remaining inclusive amount.  Remaining becomes exact zero. ## Accounting export

`metering_billing.AccountingExportService` copies one stored invoice draft, payment receipt, credit adjustment, collection write-off, leftover refund, parked leftover, leftover apply, issued-invoice void, or issued-credit-note void into an append-only `accounting_journal_proposal`.  Draft identity is `(tenant_account_id, invoice_draft_id, source_payload_hash, proposal_contract_version)`.  Cash identity is `(tenant_account_id, payment_receipt_id, source_payload_hash, proposal_contract_version)`.  Credit identity is `(tenant_account_id, credit_adjustment_id)`.  Write-off identity is `(tenant_account_id, collection_write_off_id)`.  Refund identity is `(tenant_account_id, unapplied_cash_refund_id)`.  Leftover identity is `(tenant_account_id, unapplied_cash_id)`.  Apply identity is `(tenant_account_id, unapplied_cash_application_id)`.  Void identity is `(tenant_account_id, issued_invoice_void_id)`.  Credit-note void identity is `(tenant_account_id, issued_credit_note_void_id)`.  An identical replay returns the same `proposal_id`.  Credit accept already composes the credit journal; `propose_credit_journal` and `POST /v1/credit-adjustments/{credit_adjustment_id}/journal-proposals` are the explicit compose or replay.  Void accept does not compose; `propose_void_journal` and `POST /v1/issued-invoice-voids/{issued_invoice_void_id}/journal-proposals` are the explicit compose.  Issued-credit-note void accept does not compose; `propose_credit_note_void_journal` and `POST /v1/issued-credit-note-voids/{issued_credit_note_void_id}/journal-proposals` are the explicit compose.  Untaxed draft lines debit `accounts_receivable` and credit `usage_revenue`.  Taxed draft lines debit `accounts_receivable` for the inclusive amount, credit `usage_revenue` for the exclusive amount, and credit `tax_payable` for the tax amount.  Cash lines debit `cash_receipt` and credit `accounts_receivable`.  Untaxed credit lines debit `usage_revenue` and credit `accounts_receivable`.  Taxed credit lines debit `usage_revenue` and `tax_payable` and credit `accounts_receivable`.  Write-off lines debit `write_off_expense` and credit `accounts_receivable`.  Refund lines debit `unapplied_cash` and credit `cash_receipt`.  Leftover-park lines debit `cash_receipt` and credit `unapplied_cash`.  Leftover-apply lines debit `unapplied_cash` and credit `accounts_receivable`.  Untaxed void lines debit `usage_revenue` and credit `accounts_receivable`.  Taxed void lines debit `usage_revenue` and `tax_payable` and credit `accounts_receivable`.  Untaxed credit-note void lines debit `accounts_receivable` and credit `usage_revenue`.  Taxed credit-note void lines debit `accounts_receivable` and credit `usage_revenue` and `tax_payable`.  The void proposal binds the original invoice journal by Billing `proposal_id` / stored invoice-draft journal identity only and never emits `journal_entry_id`.  The credit-note void proposal binds the original credit journal by Billing `proposal_id` plus `credit_adjustment_id` / `issued_credit_note_id` only and fails closed if that original is missing.  Status stays inside the proposal lifecycle and is never `posted`.  Compose fail-closes when any line debit or credit has more than six significant fractional digits and does not round into `numeric(38, 6)`.  AIS next pulls validated proposals.  This path does not open fiscal periods, resolve statutory account IDs, change collection outstanding, call a payment provider, or flip `proposal_status` after a pull.

## Collection case

`metering_billing.CollectionCaseService` opens an append-only commercial collection case from one stored invoice draft.  Identity is `(tenant_account_id, invoice_draft_id)`.  Outstanding equals the exact draft total.  An identical replay returns the same `collection_case_id`.  Status stays `open` or `dunning` until a receipt, a same-time credit, a later issued-credit-note application, or an explicit settle-when-zero command settles remaining outstanding to zero, or a dispute hold flips the case to `disputed` without changing remaining.  Dunning events are commercial reminders (`first_notice`, `overdue_notice`) and do not capture money or change AIS books.  New dunning fails closed while the case is `disputed`.

## Payment intent

`metering_billing.PaymentIntentService` projects one provider-neutral `payment_intent` from a stored collection case.  Identity is `(tenant_account_id, collection_case_id, source_payload_hash, payment_intent_contract_version)`.  The hash covers the case outstanding, currency, and stored status snapshot. ## AIS outbox drain

`metering_billing.AisOutboxDrainService` drains AIS `GET /outbox-events?event_type_code=posting_receipt`.  The client reads `outbox_events` and `next_cursor` only.  Empty unpublished pages are success and perform zero receipt GETs.  For `posting_receipt`, Billing constructs `urn:cwl:accounting:posting_receipt:{proposal_id}` and `urn:cwl:accounting:general_journal:{proposal_id}` from stored `proposal_id` and matches those strings by equality.  It does not parse `payload_reference`.  The stored Billing `idempotency_key` is the only `GET /posting-receipts` query.  After a successful or existing observation, the drain POSTs `/outbox-events/{outbox_event_id}/publish`.  AIS 403 is not retried as another tenant. ## Tax assessment

`metering_billing.TaxRateService` publishes one tenant-scoped `tax_rate_schedule` and one immutable `tax_rate_version`.  Header identity is `(tenant_account_id, tax_code)`.  Version identity is `(tenant_account_id, tax_rate_schedule_id, source_payload_hash, tax_rate_contract_version)`.  Closed codes are `vat`, `gst`, and `sales_tax`.  `tax_rate` is an exact `Decimal` in `[0, 1]`.  `metering_billing.TaxAssessmentService` applies a persisted version to one invoice draft. Assess after a collection case is open fails closed.  `propose_journal` then debits `accounts_receivable` inclusive, credits `usage_revenue` exclusive, and credits `tax_payable` tax. ## Credit adjustment

`metering_billing.CreditAdjustmentService` records one commercial `credit_adjustment` against a stored invoice draft.  Identity is `(tenant_account_id, invoice_draft_id, source_payload_hash, credit_adjustment_contract_version)`.  `credit_amount` is an exact `Decimal` greater than zero and cannot exceed remaining adjustable consideration.  Currency is copied from the draft.  Closed reasons are `rating_correction`, `goodwill`, and `billing_error`.  If a collection case exists, outstanding is reduced by the same inclusive amount; remaining zero marks the case `settled`.  When a tax assessment exists, `tax_exclusive_amount` and `tax_amount` are the proportional split `round_half_even(credit_amount * tax_amount / tax_inclusive_amount)`.  A taxed journal debits `usage_revenue` and `tax_payable` and credits `accounts_receivable`.  Untaxed credits stay two-line.  An identical replay returns the same `credit_adjustment_id` and `proposal_id`.  `POST /v1/credit-adjustments` records the credit.  `GET /v1/credit-adjustments/{credit_adjustment_id}` is tenant-scoped and does not call AIS.  Operators record the credit; AIS pulls the validated three-line unwind.  This path does not post, open a fiscal period, emit statutory account IDs, call AIS, or start refund-to-card or chargeback.

## Failure policy

- Duplicate input returns the existing receipt.
- A source-event key replay with a different payload hash or contract version is a conflict.
- Attribution URNs that leave the event tenant are rejected.
- Invalid quality or meter configuration fails closed.
- Provider timeouts retain internal facts and retry idempotently.
- Existing provider objects never fail over automatically to a different provider.
- Accounting rejection does not rewrite billing facts; it creates a reconciliation exception.
